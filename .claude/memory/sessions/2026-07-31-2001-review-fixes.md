## The speed finding did not reproduce — measure, don't assume
- Review claimed `_merge`'s `concat + sort` should be `merge_sorted` for ~5-7x,
  since both inputs are already sorted. Benchmarked across 2 key sizes × 3 batch
  shapes on polars 1.43.1: **concat+sort wins 5 of 6**, e.g. 18ms vs 27ms
  appending 100 rows to a 2M-row key. Polars' sort has a fast path for
  nearly-ordered input that beats the interleave. Reverted; left a comment in
  `_merge` saying re-measure before swapping, don't swap on principle.
- Profiling the real write showed why the claim felt plausible but didn't matter:
  a 2M-row write is ~171ms total = ~60ms `_merge` + ~73ms backend write (49ms of
  that `write_parquet`). The sort was never the dominant term; the whole-key
  rewrite is, and that's the documented architectural limitation.
- **The actual lever was `row_group_size`.** Row groups are the unit the parquet
  reader can skip and *every* read here is a time range, so finer groups mean less
  over-read. Swept 8k–250k: 64k gives ~1.35x on narrow and mid reads (6.0ms →
  4.4ms on a 2M-row key) at no write or size cost. Below ~16k write cost climbs
  and wide reads regress. Set as `DEFAULT_ROW_GROUP_SIZE`; compression and fsync
  exposed as backend options alongside it.

## The two real bugs (both silent corruption)
- **Key forgery.** `canonicalize` joined `name=taggedvalue` with `&`. A string
  value containing the separators forged extra kwargs and produced an *identical*
  canonical string — so `Manifest.verify` couldn't catch it either, and
  `write(a="x&b=s:y")` then `read(a="x", b="y")` served another series' rows. My
  own earlier test (`test_nested_separator_is_not_forgeable`) passed because it
  only tried `a="1&b=2"` without the `s:` tag — a near miss that gave false
  confidence. Fixed by canonicalizing to a tagged *structure* and serializing as
  JSON, so escaping keeps every value in its own slot. **This changed digests**;
  unreleased, so old dirs just become unreachable rather than wrong.
- **Interrupted delete.** "Data first, manifest last" is only safe when an update
  *grows* what's claimed. `delete()` shrinks: data-first, interrupted, left the
  manifest claiming a range whose rows were gone, and a read then answered
  "covered and genuinely empty" — precisely the hole invariant 5 forbids. Rule is
  now "the interruptible middle state must under-claim", so shrinking updates
  write the manifest first; `StorageBackend.write` grew a `manifest_first` flag.
  Checked replace_window separately: it also removes rows but data-first is
  correct there, because the intermediate state ("covered, and this is what's in
  it") is exactly the assertion the write is making.

## Gotchas & dead ends
- `DataFrame.empty` is True for *any* frame with no columns, including one with a
  fully populated index. The facade's "upstream had nothing" check used it and
  silently dropped timestamps while still claiming coverage. Condition must be
  `columns.empty and len(index) == 0`.
- `pd.DatetimeIndex([], tz="UTC")` resolves to `datetime64[s]`, so empty reads
  didn't match non-empty `[us]` reads on concat. Spell the dtype out.
- `mkstemp` + `os.replace` isn't durable without also fsyncing the *directory*;
  without it the ordering guarantee holds against process crash but not power loss.
- ruff wanted the `Literal` alias below the imports, not wedged between them.
